`BUGFIX: Align DocumentUriPathProjection to contentGraph when varying disabled and removed tagged nodes <https://github.com/neos/neos-development-collection/pull/5971>`_
-------------------------------------------------------------------------------------------------------------------------------------------------------------------------

A newly created peer-variant of a hidden document-node would get the disabled information copied. This makes the uri-path hidden but the node is not since the created node-information in the uriPath projection will copy the disabled tag to the new node-information. The state cannot be fixed by the editor because each hide/unhide of the new variant will only raise and lower the disabled level by 1 never allowing it to become zero (visible) again.

Background: 

Currently the UriPathProjection will copy the disabled and removed informations directly from the source node when a new node variant is created.

This is incorrect as the values must be calculated using the same logic as subtree tags which are handled by the contentGraphProjection that will:
- copy all directly assigned subtree-tags to during ``createSpecializationVariant``
- NOT copy subtree-tags at all for ``createPeerVariant`` and ``createGeneralizationVariant``

This change brings the behavior of the documentUriProjection in line and ensure that ``disabledLevel`` and ``removedLevel`` are calculated from the information of the parentNode adjusted by information from the directly assigned tags during ``createSpecializationVariant``.

`BUGFIX: Add primary keys to DocumentUriPathProjection and AssetUsage tables <https://github.com/neos/neos-development-collection/pull/5990>`_
----------------------------------------------------------------------------------------------------------------------------------------------

This PR converts two unique indizes on **DocumentUriPathProjection and AssetUsage** tables into primary keys.

The tables don't have primary keys yet, which is recommanded for innodb tables. Also some hosting providers try to ensure this with the MySQL option ``sql_require_primary_key = ON``.

I changed the existing migration for asset usage, to allow users to install Neos in database systems with  ``sql_require_primary_key = ON``. Otherwise the install process will fail even if a followup migration would fix the missing PK. A second migration will only apply if the non-fixed migration was already applied.

This PR intenionally doesn't fix the missing PK on the HierarchyRelation table, as it has no existing unique key to re-use in Neos <9.2. That's why it will be fixed in >= 9.2 only (https://github.com/neos/neos-development-collection/pull/5991).

See also: https://mariadb.com/docs/server/server-management/install-and-upgrade-mariadb/migrating-to-mariadb/migrating-to-mariadb-from-sql-server/understanding-mariadb-architecture#primary-key-and-indexes

> If an InnoDB table doesn't have a user-defined primary key, the first UNIQUE index whose columns are all NOT NULL is used as a primary key. If there is no such index, the table will have a clustered index. The terminology here can be a bit confusing for SQL Server and other DBMS users. A clustered index in InnoDB is a 6 bytes value that is added to the table. This index and its values are completely invisible to the users. It's important to note that clustered indexes are governed by a global mutex that greatly reduces their scalability.

> Some consequences of these design choices are the following:
For performance reasons, a primary key value should be inserted in order. In other words, the last inserted value should be the highest. This order is normally followed when inserting values into an AUTO_INCREMENT primary key. The reason is that inserting values in the middle of an ordered data structure is slower, unless they fit into existing holes. If we insert primary key values randomly, InnoDB often has to rearrange pages to make some room for the new data.
A big primary keys means that all secondary indexes are also big.
A query by primary key will require a single search. A query on a secondary index that also reads columns not contained in the index will require one search on the index, plus one more search for each row that satisfies the index condition.
We shouldn't explicitly include the primary key in a secondary index. If we do so, the primary key column will be duplicated in the index.

Fixes partially `#5988 <https://github.com/neos/neos-development-collection/issues/5988>`_

`BUGFIX: Fix and declare compatibility for MySQL 9.7 <https://github.com/neos/neos-development-collection/pull/6025>`_
----------------------------------------------------------------------------------------------------------------------

Previously the test would fail with

> Syntax error or access violation: 3143 Invalid JSON path expression. The error is around character position 7

The reason for this is the ``CONCAT`` expression for this example returning ``$.tag-1`` which is not a valid json path but needs to be quoted.

```sql
SELECT t.tag
FROM JSON_TABLE(JSON_KEYS('{"tag-1": true, "tag-2": false}'), '\\$[*]' COLUMNS (tag VARCHAR(30) PATH '\\$')) t
WHERE JSON_CONTAINS_PATH('{"tag-1": true}', 'all', CONCAT('\\$.', t.tag)) = 0
```

We cant use the ``QUOTE`` function as it introduces single quotes. But its safe to use double quotes just around as the subtree tags are constraint to not include them: ``^[a-z0-9_.-]{1,36}$``

`BUGFIX: Keep cache segment markers after resolving dynamic segments in cached segments <https://github.com/neos/neos-development-collection/pull/5998>`_
---------------------------------------------------------------------------------------------------------------------------------------------------------


> [!NOTE]
> This bug was found with AI assistance while analyzing a Redis dump of the content cache from a production site. The tests and this description were generated by AI as well. The fix itself is a two-line change that restores one state flag. It was verified against a real Neos 8.4 project and the Neos.Fusion test suite, and is already being trialed on our customers' sites. I will post an update with the results in the next few days.


This fixes a case where the content cache stores nested cached segments **inline as plain HTML** in the entry of their outer segment instead of as placeholders. Afterwards, those nested segments and the dynamic segments inside them can no longer be flushed by their own tags. The outdated content stays visible until the outer segment is flushed.

It happens when an outer ``cached`` or ``dynamic`` segment is rendered again while its nested segments are still in the cache, and one of those nested cache hits contains a ``dynamic`` segment:

```
outer (cached)              <- re-rendered (e.g. after editing a content element)
├── first  (cached, hit)
│   └── dynamic segment     <- resolved as its own entry point, which resets the flag
└── second (cached, hit)    <- now embedded WITHOUT markers -> frozen in "outer"
```

A typical real-world occurrence: a page's main ``ContentCollection`` contains sections (cached), and each section contains a dynamic listing. After an editor changes any element on that page, the listings of all following sections are frozen in the collection's cache entry. Newly published items never show up there, even though the listing tags are flushed correctly.

**Cause:** In ``RuntimeContentCache::preEvaluate()``, the callback for ``evalCached=`` makes the dynamic segment its own cache entry point by setting ``inCacheEntryPoint = null``, and restores that state afterwards. When the nested entry point finishes, ``postProcess()`` also resets ``addCacheSegmentMarkersToPlaceholders`` to ``false``, but this flag was not restored. The rest of the outer cache miss was then rendered as if it were no cache miss: following cache hits were returned without segment markers and ended up inline in the outer cache entry.

**Fix:** Save ``addCacheSegmentMarkersToPlaceholders`` before resolving the dynamic segment and restore it afterwards, just like ``inCacheEntryPoint``:

```php
$previouslyInCacheEntryPoint = $self->inCacheEntryPoint;
$previouslyAddCacheSegmentMarkersToPlaceholders = $self->addCacheSegmentMarkersToPlaceholders;
$self->inCacheEntryPoint = null;
// ... evaluate the dynamic segment ...
$self->inCacheEntryPoint = $previouslyInCacheEntryPoint;
$self->addCacheSegmentMarkersToPlaceholders = $previouslyAddCacheSegmentMarkersToPlaceholders;
```

related: #1958, `#1960 <https://github.com/neos/neos-development-collection/issues/1960>`_

**Upgrade instructions**

None. Cache entries that were already stored with inline content are only corrected after they are flushed. Flushing the ``Neos_Fusion_Content`` cache once after the update fixes all of them.

**Review instructions**

The new data-provider test ``ContentCacheTest::nestedSegmentsAreStillFlushableAfterOuterSegmentWasRerendered`` covers the affected nesting variants plus one control case. Each case does the following:

1. Render with ``testArgument = 1``, so everything is cached.
2. Flush ``outer`` and render again. The nested segments are cache hits, so this is where the bug kicks in.
3. Set ``testArgument = 2``, flush ``leaf`` (the tag of the dynamic segments) and render twice.

| Data set | Before (without fix) | After (with fix) |
|---|---|---|
| cached outer, cached segments containing dynamic segments | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| dynamic outer, cached segments containing dynamic segments | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing dynamic segment followed by dynamic segment | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing dynamic segment with disabled discriminator | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing **uncached** segment (control) | ✅ ``First\\|2\\|Second\\|2`` | ✅ ``First\\|2\\|Second\\|2`` |

**All nesting combinations**

To make sure the fix does no harm elsewhere, I ran an additional matrix test, which is not part of this PR because of its runtime of ~5 minutes. It covers every combination of the modes ``none``, ``cached``, ``uncached``, ``dynamic`` and ``dynamic`` with ``entryDiscriminator = false`` for this structure:

```
outer > child A > grandchild a > value
      > child B > grandchild b > value
```

That is 5⁵ = 3125 combinations, each in 4 flush scenarios (baseline, flush outer, flush child A, flush child B), so 12,500 cases. Each case checks the output after every step against the expected fresh rendering.

The 48 failing combinations are exactly those where:

- child A is a ``cached`` hit containing a ``dynamic`` segment (with ``'static'`` or ``false`` discriminator), and

No other combination changes its behavior. I can share the generator script and the matrix test if you want to run them yourself.

`BUGFIX: Prevent slow db session after `optimizer_switch="derived_merge=off"` <https://github.com/neos/neos-development-collection/pull/6001>`_
-----------------------------------------------------------------------------------------------------------------------------------------------

With https://github.com/neos/neos-development-collection/pull/5537 we set the SQL flag ``derived_merge=off`` to enable support for MySQL. Otherwise

> General error: 1210 Incorrect arguments to JSON_TABLE

will be thrown.

The switch will be set in the content graph projection for any ``NodeAggregateWasMoved`` event with a new parent (not sorting among siblings)

The problem is that other SQL queries are no longer optimised via the ``derived_merge`` optimisation for the whole time of the session. This might explain exceptional long query times in the content cache catchup hook queries and also in the subsequent compute changes queries for the workspace module which are otherwise not that slow.

Now we use a single comment optimiser hint https://dev.mysql.com/doc/refman/8.4/en/optimizer-hints.html#optimizer-hints-table-level which is only set for the current query on the CTE table ``r`` which is used in the ``JSON_TABLE``

A possible alternative is `#5879 <https://github.com/neos/neos-development-collection/issues/5879>`_where we fully change subtree tag writing to be managed more by PHP

`TASK: Graph State Tests <https://github.com/neos/neos-development-collection/pull/5823>`_
------------------------------------------------------------------------------------------

This adds a new test suite, mainly to cover publishing.

The general idea is to make postcondition checks purely based on state, not identity. Since we have no clear concept of identity for nodes and edges, we can't know whether we got the right version of a node or its relatives. What we can assert, though, is whatever we fetched matches the users' expectations - by having a certain state (which includes identity properties like workspace name, node aggregate id and origin dimension space point, but also properties, subtree tags, timestamps and so on).
This makes comparing workspace states rather easy, especially in regard to the planned changes in https://github.com/neos/neos-development-collection/pull/5776 and the concept of state-based publishing. It also does not violate the idea of behavioral tests as it still describes the system's behavior.
