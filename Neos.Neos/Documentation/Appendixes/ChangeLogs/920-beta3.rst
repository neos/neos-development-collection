### History

Originally the event publication in the workspace command handler was obscured via recursions.
With https://github.com/neos/neos-development-collection/pull/5315 Neos 9 - as released today - was refactored to transparently return all events to publish back to the ``ContentRepository::handle()`` instead of publishing some events one-selves.

That change as an absolute required step at the time but ironically only showed the real problem at hand - that there are absolutely no guarantees for 100% concurrency safety.

At that time we did not realise this fully and its implication but rather attempt to implement a remediation strategy in case the event store rejected some events where its now absolutely required to commit a final event before still aborting  to restore the state.

We called that "control-flow-aware" command handler and the ``WorkspaceCommandHandler`` was the one only needing that.

For more detail's see also Publish V3 which is the implementation shipped for Neos 9.0 and 9.1 https://github.com/neos/neos-development-collection/pull/5301

### Advantages of returning all events to publish from the command handlers

A primitive implementation of event sourcing might just go ahead and use the event-store and their event-normaliser to normalise and commit the events directly from within the command handler.
This is not wrong but the Neos CR as of now returns all events bravely from their command handlers for later commit.

This brings following advantages:
- We ensure that a command-handler evaluates a command to exactly one batch of events
- We ensure that commands are never a noop but rather enforce the convention of throwing exception like ``WorkspaceCommandSkipped``
- We can enrich all the events with meta-data which can thus never be forgotten - adding userId, timeStamp but also the correlationId based on the actual command - not their possibly serialised counter-form
- We can add performance time markers to time correctly how long the computation to calculate the events costed separately of their commit
- The command-hook ``onAfterHandle()`` expects to receive all ``PublishedEvents`` of the command and can do so safely without us looking back into the event-store and possibly encountering simultaneous events written from foreign streams 

### Removes now obsolete content stream closing

Content stream closing was introduced to fix https://github.com/neos/neos-development-collection/issues/4680. The closing was required at that time as commands referenced a contentStreamId to write on instead of a workspaceName which exactly produced this race condition. Also old content streams were at that time not immediately cleaned up with ``ContentStreamWasRemoved`` allowing to write inaccessible content.

The above mentioned Publishing V3 introduces here bit more stability but also a little chaos see https://github.com/neos/neos-development-collection/pull/5342 and even later https://github.com/neos/neos-development-collection/pull/5829 - content stream closing did not turn out to be the best idea.

Now if we were to commit all events at once where the last event in the batch is the content stream removal event asserting that no new events occurred on the stream and that the stream is afterwards closed/removed, we do not longer run into this problem. 

**Needs ``cr:setup``** ⚠️ 

The database schema was adjusted to drop the ``closed`` column in the content stream table.
Failing to drop it before catching up new events results in:

> General error: 1364 Field 'closed' doesn't have a default value

1.) ANY previously possible invalid content stream closed state

The latest patches of 9.0 and 9.1 fixes (TM) a long standing bug where content streams were left closed after the transaction had a failure.
Now we categorically exclude this kind of problem.

2.) 9.2-dev introduces more constraint checks for workspaces https://github.com/neos/neos-development-collection/pull/5488

This looks good in theory in first sight and definitely prevents race-conditions but also has the side-effect that due to the new constraint checks a later batch of events _could_ now fail in a race condition.
A possible failure was not anticipated in that pr leading during publishing possible to a new kind of but where a content stream is left closed.

See comment https://github.com/neos/neos-development-collection/pull/5488#discussion_r3620484369 for more details

Now fixed because we commit all events at once and we dont need to think of recovery strategies of partially committed events.

3.) No prune-able content streams after race-condition in workspace creation

Workspace creation was made thread-safe via https://github.com/neos/neos-development-collection/pull/5860.
But as before two events were committed where the second event could fail in a race condition we had to catch the concurrency exception and revert the first committed ``ContentStreamWasForked`` by removing that content stream appending an ``ContentStreamWasRemoved`` event. Instead these two events are rather obsolete and should not be needed to be emitted.

Because we commit a batch of events now where either all constraints pass or the whole batch is rejected we no longer phase this weirdness.

4.) Adjust parallel test of ``ChangeBaseWorkspace`` to ignore ``ContentStreamDoesNotExist`` exception

see https://github.com/neos/neos-development-collection/pull/5888#issuecomment-4803436419

5.) Unexpected not yet discovered race-conditions

Using an atomic ``commitAll()`` is the safer bet for every scenario. The events are calculated first based on the current state and later only we commit the batch of events and even later do the catchup. All thinkable scenarios where only partial events might get committed due to $any reason like even a well meant bugfix (see 2) are solved for now and the future (TM).

### Foundation for a race condition safe ``ContentStreamWasForked`` event

Emitting fork events is not safe during parallel executions: https://github.com/neos/neos-development-collection/pull/5830

Before the introduction of the eventstore's ``commitAll()`` and the possibility to use the new API ``Neos\\EventStore\\Model\\EventsForCommit::withExpectedVersionForStream()`` it was also not possible to express the guarantees needed.

Now with the refactoring here and the foundations introducing the ``EventsToPublish`` with the same ability we can in a future PR solve this race-condition:

## Concept

### Original Query, now replaced: MAX(...) GROUP BY id in a derived table
 
This approach was fast in MariaDB but slow in MySQL.
 
The approach explained step by step:
 
1) We essentially want to run ``SELECT MAX(contentstreamlayer) WHERE id = ... AND contentstreamlayer IN (:contentStreamLayers)``
 once per id, but more efficiently. To resolve a whole set of ids in one query, we turn the per-id MAX into a grouped one:
 
```sql
 SELECT id, MAX(contentstreamlayer) AS contentstreamlayer
       FROM {hierarchyRelation()}
       WHERE contentstreamlayer IN (:contentStreamLayers)
       GROUP BY id
 ```
This yields one (id, winning-layer) pair per id.
 
2) That pair only tells us which layer wins (for a given id); we still need the full row ``h.*``. Selecting any other columns
 is undefined behavior and forbidden in strict mode via only_full_group_by. Thus treat the grouped result as a derived table
 ``readHierarchy`` and INNER JOIN the original table back onto it, matching on (id, winning-layer).
 The INNER JOIN also drops any id that had no row in the allowed layers.
 
WHY IT WAS REPLACED: MySQL cannot optimize this. The derived table ``readHierarchy`` has ``GROUP BY id``, and MySQL
has no way to push the outer join key (id) into a grouped derived table, so it materializes the full grouped
result for every lookup.
 
 
### This PR: anti-join via NOT EXISTS
 
Restating Attempt 1 mathematically, with L = the allowed layers (:contentStreamLayers):
- for each id, compute m(id) = MAX{ layer : layer ∈ L }
- keep row h where h.id = id AND h.layer = m(id)         -- i.e. the greatest layer per id
- in symbols: h.layer ∈ L  ∧  h.layer = max{ layer ∈ L for id }
 
This is equivalent to: "no row of the same id has a layer in L strictly greater than h.layer", i.e.
 
h.layer ∈ L  ∧  ¬∃ same-id row with (layer ∈ L ∧ layer > h.layer)
 
which is exactly an anti-join (NOT EXISTS):
 
```sql
SELECT h.* FROM hr h
   WHERE h.layer IN L [AND id-prefilter]
     AND NOT EXISTS (
         -- exists a row with same id and bigger layer? -> then the current row is NOT the highest
         -- layer and we DISCARD it.
         SELECT 1 FROM hr hWin
         WHERE hWin.id = h.id AND hWin.layer IN L AND hWin.layer > h.layer)
```
 
The NOT EXISTS form stays flat and mergeable, lets the optimizer push predicates and use the
``UNIQ_id_layer (id, contentstreamlayer)`` index, and avoids materialization on both MySQL and MariaDB.

### The new real Value Object Queries and the little Framework glue 

Before in 9.0 fetching the hierarchies for a content stream was simple as the hierarchy relations contained a content stream column:

```php
->innerJoin('pn', $this->tableNames->hierarchyRelation(), 'ph')
->where('ph.contentstreamid = :contentStreamId')
->setParameter('contentStreamId', $contentStreamId->value)
```

Now the introduction of hierarchy layers requires us to now write a subquery. As the subquery is complex and often times reused a Query Value object in form of a "HierarchyRelationStatement" (here renamed) was introduced.

We see this silently still requires some content stream information - now as part of the layers int array to be present in the bound parameters. But this is in-transparent in the following form:

```php
->innerJoin('pn', $this->hierarchyRelationStatement->toSql(), 'ph')
->setParameter('contentStreamLayers', $contentStreamLayers->toIntArray(), ArrayParameterType::INTEGER)
```

This PR introduces framework code and an advanced Hierarchy relation subquery object which encapsulates bound parameters itself and the sql to be able to use that as:

```php
->innerJoinTableSubquery('pn', $this->subqueries->forHierarchyRelation($contentStreamLayers), 'ph')
```

internally we will be using a ``Neos\\ContentRepository\\Dbal\\Query\\QueryBuilder`` which just extends the ``DBALQueryBuilder`` by adding

```php
public function innerJoinTableSubquery(string $fromAlias, SqlTableSubqueryInterface $tableSubquery, ...);
```

a subquery is an object which provides its parameters and types as well as its sql

```php
/**
 * Represents a SQL "table_factor"
 *
 * To be used inside FROM and JOIN "table_references"
 *
 *     SELECT *
 *       FROM {$sqlTableFactor->toSql()}
 *
 *     SELECT *
 *       FROM my_table
 *       JOIN {$sqlTableFactor->toSql()} ON a = b
 *
 * @internal
 */
interface SqlTableSubqueryInterface
{
    public function getParameters(): Parameters;

    /**
     * Returned SQL must be valid in syntax
     *
     *     table_subquery
     *
     * {@link https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/joins/join-syntax}
     */
    public function toSql(): string;
}
```

now inside of ``innerJoinTableSubquery()`` we can merge the parameters and do the join in a single step.

### The actual performance optimisations

Because the subquery can now contain all parameters it needs and is fully encapsulated we can start adding all the performance optimisation logic we need from `#5873 <https://github.com/neos/neos-development-collection/issues/5873>``_ in a speaking manner like ``$hierarchyRelationQuery->withDimensionSpacePoint($dimensionSpacepoint)``  or  ``withDimensionSpacePoints()``  or ``withParentNodeAnchor()`  etc.

Internally the ``HierarchyRelationSubquery``  can decide to use sebastians's pre-filtering while keeping our code easy to read and without any dangerous repetitions.

### Bargain. Further abstracted queries vs plain SQL

There were times i was convinced even the doctrine query builder is in our way and we want to write the queries in pure SQL. But that is highly unpractical and we _where_ at this point years ago and the content repository was refactored to use the query builder and later more abstractions like the node query builder were introduced. So i cant help to agree that we need a chain-able query building that allows to composite parts. Currently that makes - especially CTE queries - as well as probably even every simple query no easy to manually transpose to SQL. I usually debug their concatenated SQL.

So the herby introduced _further_ abstraction instead going back to the roots is a commitment to the full shift of abstracted query building and move away from pure SQL. But the part that convinced me is not just done for aesthetic reasons - no it allows some serious performance improvements under the hood without any our by doing.

A manual explicit approach to the same optimisations would require the calling site to add an additional pre filtering where clause via ``withPossibleWhereCondition()``.

In the original commit https://github.com/neos/neos-development-collection/pull/5873/changes/`5e286d9cc6f98c60faebab9a7534f1d713c563ca <https://github.com/neos/neos-development-collection/commit/5e286d9cc6f98c60faebab9a7534f1d713c563ca>`_ it can be seen how this quickly escalated and how many duplications arose.

**Before**

```php
$hierarchyQuery = $this->hierarchyRelationQuery
    ->withWhereCondition('h.dimensionspacepointhash = :dimensionSpacePointHash')
    ->withPossibleWhereCondition('h.dimensionspacepointhash = :dimensionSpacePointHash AND childnodeanchor = :parentNodeAnchorPoint')

$sqlStatement = <<<SQL
SELECT *
  FROM {$query->toSql()}
WHERE h.childnodeanchor = :parentNodeAnchorPoint
SQL;

$this->fetchAssociative(
    $sqlStatement,
    ['contentStreamLayers' => ..., 'dimensionspacepointhash' => ..., 'parentNodeAnchorPoint' => ...],
    ['contentStreamLayers' => ArrayParameterType::STRING],
);
```

**After**

```php
$hierarchyQuery = $this->hierarchyRelationQuery
    ->withDimensionSpacePoint($dimensionSpacePoint)
    ->withParentNodeAnchor($parentNodeAnchor)

$sqlStatement = <<<SQL
SELECT *
  FROM {$query->toSql()}
SQL;

$this->fetchAssociative(
    $sqlStatement,
    $hierarchyQuery->getParameters()->toDbalValues(),
    $hierarchyQuery->getParameters()->toDbalTypes(),
);
```

The further abstraction is to those who know SQL and want to fully understand the queries and optimise them possibly a little in way but for those cases the SQL queries must be extracted from the query log or via debug. It might come in handy - for the query log, and also for the db performance schemas - to allow to identify a query uniquely but a comment.

Any further optimisations we might found out should then rather profit again from this new declarative approach as because we just define what we want to query we are not interested in its exact implementation. For example we can remove the inner pre-filtering again or move the outer ``WHERE`` clauses from the subquery out into the main query to filter the hierarchies matched on that alias.

### Caveats

Certain operations that affect lots of hierarchy entries will become copy-fork-like and thus slow. That includes for example moving a dimension space point or removing the site node. We can safely assume that this is a good bargain as these actions are not carried out by an end-user of Neos.

`TASK: Provide event migration for rebases on already removed content streams <https://github.com/neos/neos-development-collection/pull/5927>`_
-----------------------------------------------------------------------------------------------------------------------------------------------

Upgrade to deduplicate illegal concurrent workspace rebases

See issue https://github.com/neos/neos-development-collection/issues/5849

Content stream forking was not thread safe before not expressing the assertion to the source content stream
e.g. that the ``sourceContentStreamVersion`` should match the reality in the event store.
This resulted in the possibility that a source content stream was not constraint from being forked when it was already removed.
The resulting illegal ``ContentStreamWasForked`` event and its ``RebaseWorkspace`` sequence must be removed.

Required to ensure 9.2 can be replayed. Otherwise the graph will reject this event - in Neos 9.0 and 9.1 this was ignored accidentally

> Content stream "cs-review-first" does not exist. No layers found.

### 

The upgrade first determines any ``ContentStreamWasForked`` events where the source content stream was already removed via ``ContentStreamWasRemoved``.
We assume all illegally found forks are restricted to being caused by a ``RebaseWorkspace`` command (via correlation id).
Further we expect a simple ``RebaseWorkspace`` without any changes on the "user" workspace but just an empty fork.
On this empty fork we expect only a new second ``RebaseWorkspace``, starting with a ``ContentStreamWasClosed`` event or nothing if the event stream ended.
This second ``RebaseWorkspace`` is either also illegal and to be removed or a valid rebase if the source content stream existed at that point.
If valid we want to keep this rebase, but a rebase sequence refers to its previous content stream to remove it and indicate projections which was the last. The original information is no longer valid as we have removed the existence of the original previous content stream. Instead we need to patch the events to use the previous content stream of the first illegal fork - the previous-previous content stream.
Thus we patch the field ``$previousContentStreamId`` of the ``WorkspaceWasRebased`` event and rewrite the
``ContentStreamWasClosed`` and ``ContentStreamWasRemoved`` events to affect the now new last content stream.

After the migration is applied the workspace will have its last successfully rebased content stream as without the migration,
but we deduplicated any temporary illegal rebases that happened in a race condition. No content on the workspaces is affected.

`TASK: Add upgrade to deduplicate parallel base workspace changes  <https://github.com/neos/neos-development-collection/pull/5884>`_
------------------------------------------------------------------------------------------------------------------------------------

based on `#5858 <https://github.com/neos/neos-development-collection/issues/5858>`_

Upgrade to deduplicate parallel base workspace changes

for bug https://github.com/neos/neos-development-collection/issues/5877

Workspace operations, also ChangeBaseWorkspace were not thread safe before the addition of workspace versioning
in the read model and thus safe soft constraint checks.
That resulted in the possibility that a single workspace was changed two or more times in parallel by the same user.
Because each ChangeBaseWorkspace can be slow and cleans up at the end the content stream via ContentStreamWasRemoved,
that results in possibly multiple illegal ContentStreamWasRemoved events and in total a fully illegal ChangeBaseWorkspace.

The upgrade first identifies any duplicate ContentStreamWasRemoved events on a single stream.
If found we assume check via their unique prefixed correlation id that they belong to a ChangeBaseWorkspace sequence.
Then we find all events of the ChangeBaseWorkspace sequences and that occurred during these the content stream removals.
If there ar no other concurrent changes on our workspace - which would have been illegal as well - and it's truly
the race condition as understood with only the events a ChangeBaseWorkspace emits we continue.
We identify the last and thus valid ChangeBaseWorkspace sequence and delete all events from the previous illegal sequence(s).
The ChangeBaseWorkspace sequences can even be interlaced due to the race condition but the correlation id identifies the last sequence to keep uniquely.

After the migration is applied the workspace will have the same new base workspace as without the migration,
but we deduplicated any temporary changes that happened in a race condition. No content on the workspaces is affected.


for further insights, please see behaviour tests ``EventsDeduplicateBaseWorkspaceChangesUpgrade`` as to what cruelties we must handle

Now this new test shows that 9.2 solves this problem as it contains https://github.com/neos/neos-development-collection/pull/5488. 

~Note: The tests dont actually fail on 9.0 as the graph did permit a duplicate content stream removal - only with the merge of the 9.2 layers test would fail if we were not thread safe - but we are now. - Tested locally.~
Edit: We now check the events to assert validity

Additionally there is an event migration https://github.com/neos/neos-development-collection/pull/5884 to repair old events
