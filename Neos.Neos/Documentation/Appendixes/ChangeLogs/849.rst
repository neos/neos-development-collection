`BUGFIX: Keep cache segment markers after resolving dynamic segments in cached segments <https://github.com/neos/neos-development-collection/pull/5998>`_
---------------------------------------------------------------------------------------------------------------------------------------------------------


> [!NOTE]
> This bug was found with AI assistance while analyzing a Redis dump of the content cache from a production site. The tests and this description were generated by AI as well. The fix itself is a two-line change that restores one state flag. It was verified against a real Neos 8.4 project and the Neos.Fusion test suite, and is already being trialed on our customers' sites. I will post an update with the results in the next few days.


This fixes a case where the content cache stores nested cached segments **inline as plain HTML** in the entry of their outer segment instead of as placeholders. Afterwards, those nested segments and the dynamic segments inside them can no longer be flushed by their own tags. The outdated content stays visible until the outer segment is flushed.

It happens when an outer ``cached`` or ``dynamic`` segment is rendered again while its nested segments are still in the cache, and one of those nested cache hits contains a ``dynamic`` segment:

```
outer (cached)              <- re-rendered (e.g. after editing a content element)
├── first  (cached, hit)
│   └── dynamic segment     <- resolved as its own entry point, which resets the flag
└── second (cached, hit)    <- now embedded WITHOUT markers -> frozen in "outer"
```

A typical real-world occurrence: a page's main ``ContentCollection`` contains sections (cached), and each section contains a dynamic listing. After an editor changes any element on that page, the listings of all following sections are frozen in the collection's cache entry. Newly published items never show up there, even though the listing tags are flushed correctly.

**Cause:** In ``RuntimeContentCache::preEvaluate()``, the callback for ``evalCached=`` makes the dynamic segment its own cache entry point by setting ``inCacheEntryPoint = null``, and restores that state afterwards. When the nested entry point finishes, ``postProcess()`` also resets ``addCacheSegmentMarkersToPlaceholders`` to ``false``, but this flag was not restored. The rest of the outer cache miss was then rendered as if it were no cache miss: following cache hits were returned without segment markers and ended up inline in the outer cache entry.

**Fix:** Save ``addCacheSegmentMarkersToPlaceholders`` before resolving the dynamic segment and restore it afterwards, just like ``inCacheEntryPoint``:

```php
$previouslyInCacheEntryPoint = $self->inCacheEntryPoint;
$previouslyAddCacheSegmentMarkersToPlaceholders = $self->addCacheSegmentMarkersToPlaceholders;
$self->inCacheEntryPoint = null;
// ... evaluate the dynamic segment ...
$self->inCacheEntryPoint = $previouslyInCacheEntryPoint;
$self->addCacheSegmentMarkersToPlaceholders = $previouslyAddCacheSegmentMarkersToPlaceholders;
```

related: #1958, `#1960 <https://github.com/neos/neos-development-collection/issues/1960>`_

**Upgrade instructions**

None. Cache entries that were already stored with inline content are only corrected after they are flushed. Flushing the ``Neos_Fusion_Content`` cache once after the update fixes all of them.

**Review instructions**

The new data-provider test ``ContentCacheTest::nestedSegmentsAreStillFlushableAfterOuterSegmentWasRerendered`` covers the affected nesting variants plus one control case. Each case does the following:

1. Render with ``testArgument = 1``, so everything is cached.
2. Flush ``outer`` and render again. The nested segments are cache hits, so this is where the bug kicks in.
3. Set ``testArgument = 2``, flush ``leaf`` (the tag of the dynamic segments) and render twice.

| Data set | Before (without fix) | After (with fix) |
|---|---|---|
| cached outer, cached segments containing dynamic segments | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| dynamic outer, cached segments containing dynamic segments | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing dynamic segment followed by dynamic segment | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing dynamic segment with disabled discriminator | ❌ ``First\\|2\\|Second\\|1`` | ✅ ``First\\|2\\|Second\\|2`` |
| cached outer, cached segment containing **uncached** segment (control) | ✅ ``First\\|2\\|Second\\|2`` | ✅ ``First\\|2\\|Second\\|2`` |

**All nesting combinations**

To make sure the fix does no harm elsewhere, I ran an additional matrix test, which is not part of this PR because of its runtime of ~5 minutes. It covers every combination of the modes ``none``, ``cached``, ``uncached``, ``dynamic`` and ``dynamic`` with ``entryDiscriminator = false`` for this structure:

```
outer > child A > grandchild a > value
      > child B > grandchild b > value
```

That is 5⁵ = 3125 combinations, each in 4 flush scenarios (baseline, flush outer, flush child A, flush child B), so 12,500 cases. Each case checks the output after every step against the expected fresh rendering.

| | Failing cases |
|---|---|
| Without fix | **48** of 12,500, all ``flush outer`` → upper described test-behavior  |
| With fix | **0** of 12,500 |

The 48 failing combinations are exactly those where:
- the outer segment is ``cached`` or ``dynamic``,
- child A is a ``cached`` hit containing a ``dynamic`` segment (with ``'static'`` or ``false`` discriminator), and
- child B depends on its own cache entry (``cached`` or ``dynamic`` child, or a ``cached`` / ``dynamic`` grandchild).

No other combination changes its behavior. I can share the generator script and the matrix test if you want to run them yourself.

**Further checks:**
- All ``Neos.Fusion`` functional tests (288) and unit tests (476) pass (run locally against Neos 8.4.7).
- On a real Neos 8.4 project I reproduced the original problem: page warm, only the main ``ContentCollection`` entry removed, then rendered again.
  - Without the fix, that entry contained 7 listings as inline HTML and only 1 placeholder.
  - With the fix, it contains one placeholder per section, the same as after a cold rendering.

`BUGFIX: Check if target node has parent to resolve shortcut <https://github.com/neos/neos-development-collection/pull/6000>`_
------------------------------------------------------------------------------------------------------------------------------

This checks if the node has a parent node in case the parentNode shall be the target. If no parent node was found the target is ``null``.

This can rarely happen, but if you f.e. create a node and add a shortcut as childnode (with target parentNode) and discard the creation of the parent node, this will end in a fatal error (e.g in workspace review, where the childnode is still rendered).

`TASK: Rewrite node comparison in fusion <https://github.com/neos/neos-development-collection/pull/6011>`_
----------------------------------------------------------------------------------------------------------

This adds a migration for fusion to replace node comparison which is commonly used to determine if a node is the site node or documentNode.

As the comparison in EEL is strict (``===``), it will now return ``false`` if you compare the nodes. So we need to use the aggregateId instead.

```diff
-    @if.onHomepage = ${documentNode == site}
+    @if.onHomepage = ${Neos.Node.equals(documentNode, site)}
```


see https://github.com/neos/neos-seo/issues/203
